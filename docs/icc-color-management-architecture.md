# CHR-240 — ICC color management integration decision

Status: architecture/research slice only (2026-10-06). No ICC engine, profiles, or pixel-processing code is added by this change.

## Decision

Use LittleCMS 2 through the `lcms2` Rust binding as the authoritative ICC engine for profile parsing, source-to-working-space conversion, and ICC proof transforms. Keep ICC math out of hand-written GLSL. The current camera DCP pipeline is a separate, calibrated camera-rendering operation and must remain intact; an ICC source transform should feed it only where the source is actually tagged with an ICC profile and the decode contract establishes what RGB values those bytes represent.

The Rust binding exposes owned `Profile` and `Transform` types, transforms pixel slices, supports loading profiles from in-memory ICC bytes, and documents a proofing transform with separate output and proof profiles plus rendering intents. This is a direct fit for the operations CHR-240 calls for; it avoids maintaining custom matrix/transfer-function cases per named profile. The crate documentation identifies it as a wrapper over LittleCMS and its current published crate requires Rust 1.89 or newer. [lcms2 crate](https://docs.rs/lcms2/latest/lcms2/), [Profile API](https://docs.rs/lcms2/latest/lcms2/struct.Profile.html), [Transform API](https://docs.rs/lcms2/latest/lcms2/struct.Transform.html), [crate package/build metadata](https://docs.rs/crate/lcms2/latest), [LittleCMS API manual](https://www.littlecms.com/LittleCMS2.16%20API.pdf).

## Current application boundary

- `chromasmith-22.html` owns the browser still-image path. TIFF goes through `loadTiff`: UTIF decodes to RGBA8, the code reads TIFF tag 34675, and profile handling currently branches on the human-readable profile description. Only a profile whose description contains “ProPhoto” receives the app's custom ProPhoto-to-sRGB matrix conversion; other non-sRGB profiles warn without conversion. Parsing the profile description is diagnostic and is not ICC color math.
- The browser render/export pipeline is sRGB-referred. The WebGL `FXR` pipeline produces rendered pixels; still export runs `processToCanvas` and `exportFX`, encodes through canvas `toBlob`, then applies metadata helpers. PNG receives an sRGB chunk. This is distinct from a proofing transform: a PNG sRGB tag describes output pixels; it does not simulate a printer or other proof device.
- RAW camera rendering is its own path. `bakeDcpLUT` / `applyDcpLUT` in `chromasmith-22.html` apply DNG camera matrices, look tables and tone curves; `desktop/src-tauri/src/raw_decode.rs::apply_lut_rgba` mirrors that LUT application in Rust. Do not route DCP camera RGB through a generic ICC transform without proving the input encoding and preserving the existing DCP calibration contract.
- `desktop/src-tauri/Cargo.toml` currently declares no `lcms2` dependency. Desktop native still decoding exists, but the TIFF path above is still decoded in the webview.

## Important export correctness finding

The implementation and comments currently disagree about source ICC preservation. `injectMetadataJPEG` copies all source APPn segments, including an ICC APP2 profile; `injectMetadataPNG` keeps source `iCCP` chunks. Export later adds an sRGB chunk to PNG, and adjacent comments state the source profile is not re-embedded. Once import actually converts arbitrary source profiles into sRGB, retaining that source ICC chunk would label the converted pixel values with the wrong profile. Treat this as an explicit acceptance condition for the implementation: metadata preservation must exclude/replace source ICC metadata after conversion, and output tagging must match the actual transformed bytes. Add JPEG and PNG fixtures that inspect the encoded profile markers rather than relying on the editor canvas appearance.

## Recommended first implementation boundary

1. Add a small Rust ICC service around `Profile::new_icc` and `Transform`, with explicit input/output pixel formats, rendering intent, alpha preservation, checked dimensions/byte lengths, and errors for malformed/unsupported profiles. Use profile bytes supplied by the decoder; do not select color transforms by profile description strings.
2. Route one bounded still-image import path through it first (TIFF is the current concrete profile-bearing path). Convert decoded source RGB to the app's chosen working/output encoding before constructing the canvas, replacing the ProPhoto-name special case. Keep alpha unchanged and never silently treat an unknown profile as sRGB: report the failure and retain a documented fallback policy.
3. Correct export metadata as part of the same end-to-end slice: prevent stale source ICC metadata from being copied after conversion; write/retain only the output profile metadata that describes the encoded pixels. Test TIFF → preview → JPEG/PNG round trips with sRGB, ProPhoto, and a non-ProPhoto RGB profile.
4. Add soft proofing only after source normalization and export tagging are reliable. Build a native LittleCMS proof transform from working profile, output/display profile, and proof profile, with separately chosen rendering intents and proof/gamut-check flags. It must transform real rendered pixel data (or a LUT generated from real LittleCMS transform samples and verified against LittleCMS pixel output); a hand-written shader approximation or gamut-warning heuristic is not ICC soft proof. Decide the display/preview output encoding explicitly because the current WebGL canvas does not itself apply this app's ICC proof transform.
5. Extend to other still decoders only where their metadata APIs expose the embedded ICC bytes and their decoded channel encoding is known. Keep camera DCP processing separate. Video color-space metadata and HDR transfer paths need a separate design and parity tests.

## Packaging and runtime risks to resolve before adopting the crate

- `lcms2` is a Rust wrapper around the LittleCMS C engine (the crate metadata lists `lcms2-sys`); validate how the exact locked version builds and links for each shipped macOS and Windows target before adding it. This note does not assume static bundling, a system library, or a particular build-script mode.
- Confirm the project's Rust toolchain meets the current binding's documented MSRV (1.89) and pin/review the selected crate version and its transitive native build inputs.
- Establish whether release artifacts include the required library bits, signing/notarization sees them, and the Windows installer places any runtime library in a loadable location. Test clean-machine installs for both architectures. No runtime profile file should be assumed installed on the user's machine; profiles should be passed as bytes from image metadata or selected by the user.
- ICC files are untrusted input. Bound profile and image sizes, reject malformed data without panicking, avoid blocking the webview, and test worker/thread ownership. The binding documents context-aware transforms for `Send` and that cached transforms are not `Sync` by default; choose contexts/cache flags deliberately rather than sharing global transforms across workers.
- Full-resolution transforms can allocate/copy several large buffers. Measure peak memory and processing time on representative 24 MP and larger images before routing whole-image export or RAW paths through the native boundary. A second IPC copy from webview to Rust is a material risk for the existing UTIF TIFF path; moving decode and transform together may be preferable, but is a separate architectural decision.
- License and notices: review the exact LittleCMS and Rust binding/sys-crate license obligations and include the required notices in desktop distributions before shipping.

## Bounded proof delivered by this slice

This change establishes the engine choice, identifies the existing import/render/export seams and a source-profile metadata hazard, and sets a staged implementation/verification order. It does not add a native dependency, compile LittleCMS, convert pixels, implement soft proofing, add bundled ICC profiles, or satisfy CHR-240's user-visible acceptance criteria. Follow-on work remains: validate platform build/link/package behavior; implement robust profile-based import conversion and export metadata replacement; implement actual LittleCMS proof/gamut behavior; then verify source/profile matrices, preview/export parity, performance/memory, and clean installs on macOS and Windows.
