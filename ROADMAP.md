| R12 — HDR merge (deghost+align), focus stacking | `desktop/src-tauri/src/merge.rs`, native Rust, reusing `raw_decode.rs` for the RAW half of decode (no second RAW decode path). **Alignment**: SCOPED DOWN to translation-only (2-DOF), not full affine/Euclidean ECC — said plainly rather than claimed away, per the honesty rule below. Registers by Gauss-Newton minimization of the SSD between zero-mean/unit-variance normalized reference/candidate images, coarse-to-fine over a small image pyramid; this is EXACTLY equivalent to ECC's own correlation-coefficient objective for a translation warp (Evangelidis & Psarakis, TPAMI 2008: for zero-mean/unit-norm ubar,vbar, minimizing‖ubar−vbar‖² maximizes ⟨ubar,vbar⟩), so it's a real Lucas-Kanade-style (Lucas & Kanade 1981) implementation of the SAME objective ECC targets, just without the affine/Euclidean warp Jacobian. Validated against a synthetically shifted image with a KNOWN applied offset (`tests::ecc_translation_recovers_known_shift`): recovers dx,dy within 0.6px for shifts up to 8px and 0.7px at 12px, across both axes and signs. **HDR (Mertens Exposure Fusion, Pacific Graphics 2007)**: per-pixel weight = contrast (|Laplacian|) × saturation (RGB std-dev) × well-exposedness (Gaussian around mid-grey per channel), blended via a Laplacian-pyramid multi-band blend (Burt & Adelson 1983) — directly produces an LDR result, no camera-response calibration or tone-mapping needed. Validated on a synthetic 3-exposure bracket with a deliberately clipped-white half and a deliberately crushed-black half in different frames (`tests::exposure_fusion_recovers_clipped_and_crushed_detail`): the fused output's local variance in both halves is 10×/5× the (near-zero) variance of the single exposure that ruined that half. **Deghosting**: median-outlier-rejection extension (the same idea behind `enfuse --deghosting` and Sen-et-al.-style outlier gating) — radiometrically normalizes each frame toward the reference's median log-luminance, takes the per-pixel median of the normalized stack as the "static consensus", and multiplies each frame's Mertens weight by a Gaussian falloff on its deviation from that consensus. Validated two ways on a synthetic frame with a textured "moving object" patch inconsistent with the other two frames' consistent exposure scaling (`tests::deghosting_suppresses_synthetic_moving_region`): (1) mechanistically — deghosting cuts the anomalous frame's own blend weight inside the patch by >30%; (2) at the pixel level — the deghosted fused patch sits closer to a ghost-free 2-frame reference (fused through the identical machinery) than the plain/non-deghosted fusion does. **Focus stacking**: per-pixel sharpness = variance of the Laplacian in a local window (Pertuz, Puig & Garcia, Pattern Recognition 2013 — ranks VoL among the best simple focus measures), computed via summed-area tables for O(1)-per-pixel window queries, blended with the SAME Laplacian-pyramid multi-band blender HDR fusion uses (a hard per-pixel argmax would show seams at every focus-measure crossing) — this is the deliberate code-reuse the brief asked for, not two separate blend implementations. Validated on two synthetic sources sharp in complementary halves (`tests::focus_stack_is_sharp_in_both_regions`): the stacked result measures sharp (>3× the blurred reference's variance-of-Laplacian) in BOTH halves, using the same sharpness metric the stacker itself builds from. A found-and-fixed real bug along the way: the first weight-blend pass fed each per-pixel Mertens/sharpness weight into the pyramid's FINEST level completely unsmoothed, which crossed the image's own texture band and rang (a synthetic 2-frame no-op case reconstructed at 0.14 where the true blend should sit near 0.46) — fixed by lightly blurring (then renormalizing) each weight map before it enters the pyramid, exposed as `pyramid::smooth_weight` and shared by both `hdr::fuse` and `focus::stack`. **Tauri commands** `merge_hdr_photos`/`merge_focus_photos` (both `spawn_blocking`, CPU-bound) write the result as an ordinary new PNG next to the first source photo (`merge_output_path`, collision-safe) — the cleanest integration point per the brief: no new file type, the Library just picks it up as a normal photo. **Library UI**: "Merge exposures (HDR)…"/"Focus stack…" in the multi-select context menu (`library-ui.js`'s `buildPathsMenu`, mirroring the existing "Reset edit" batch-action pattern — toast, `invoke`, `refreshView`, dimmed below 2 selections rather than hidden per CLAUDE.md §10.13's "permanently hidden is permanently unaudited" lesson), opening the merged result in the editor on success. **Honest limitations, not glossed over**: (1) alignment is translation-only, not affine — real handheld rotation/scale drift is not corrected; (2) RAW sources going into a merge get a plain linear→sRGB gamma encode, NOT the full DCP camera-profile bake (`bakeDcpLUT`) that lives in the JS editor — merge output from RAW sources will have measurably different hue/saturation than what the editor shows for that same RAW, until a future pass routes RAW decode through `apply_lut_rgba` with a chosen DCP profile; (3) no real bracketed/multi-focus test photos exist anywhere in this repo (checked `test/fixtures/`, `Best/`, `Lucifer/`) so only synthetic validation was performed — no real-photo round trip was run. That check needs a real face photo and has not been done. |

| R6 — Deconvolution sharpening | Damped Richardson-Lucy (Richardson 1972 / Lucy 1974, White 1994/Dey et al. 2006-style damping — real published techniques, not invented), modeling the lens/sensor blur as a small user-controlled Gaussian PSF and inverting it, unlike the existing unsharp-mask Sharpen/Clarity which only boosts existing edge contrast. **Validated in plain Node first** on a synthetic step-edge+noise 1D signal before touching GLSL (see the mechanism-first rule in CLAUDE.md §10): on a clean blurred edge, 6-iteration RL nearly matches unsharp-mask MSE (0.01075 vs 0.01067) while recovering more real edge slope (0.282 vs 0.271, true edge 0.900). On a NOISY blurred edge — the case that matters — plain RL clearly beats unsharp mask on both detail recovery (MSE 0.0148 vs 0.0231, edge slope 0.388 vs 0.344) AND noise amplification (flat-region variance 0.0052 vs 0.0135, i.e. unsharp amplifies noise **2.6x more**). Damped RL then measurably reduces plain RL's own ringing/noise growth at every iteration count tested (flat-region variance: 3-it 0.00397 vs 0.00467, 6-it 0.00425 vs 0.00520, 40-it 0.00545 vs 0.00744 — a 15-27% cut, growing with iteration count exactly as the "caps runaway noise amplification" theory predicts) while still recovering most of plain RL's real edge detail (edge slope 0.324 vs plain's 0.388). Ported to GLSL as its own small multi-pass sub-pipeline (`progs.deconvUpdate` + `progs.deconvMix`, reusing the EXISTING separable-Gaussian `progs.blur` program for the reblur-of-estimate step each iteration, the same architecture the halation/skin chains already use) rather than being crammed into the single-pass `lut` shader — runs right after Lens/NR, before the `lut` pass, in the `img -> lens -> nr -> deconv -> lut` chain. 3 iterations (real-time budget), damping constants `dampT=0.06, maxStep=0.35` carried over from the Node validation. New "Deconvolution" panel card (Amount + Radius sliders, mirrors the Noise Reduction card's markup/wiring) sits right after Noise Reduction. **Zero-cost when Amount=0** by construction — the whole 10-draw-call block is skipped in JS, not merely blended to identity, verified via 18/18 export goldens staying byte-exact (no shipped recipe sets `deconv`) plus 21/21 mask + perf + 0 UI-audit regressions. Real-fixture sanity check (`test/probe_deconv.mjs`, `test/fixtures/portrait.png`): edge steepness increases monotonically with both Amount and Radius (maxSlope 102.3 at Amount 0 -> 108.0 at 50% -> 113.4 at 100% -> 123.3 at 100%+wide radius), confirming the effect is real and scales as expected; SwiftShader-headless timing showed the extra pass chain adds roughly +0.02-0.16ms per frame at 1024-2048px in this measurement environment (not necessarily representative of a real GPU/interactive frame budget, but shows the overhead is a small constant, not a resolution-scaling blowup). **Honest limitation**: the PSF is a parametric Gaussian, not real per-lens/sensor calibration data — this codebase has none (no per-lens MTF database, unlike e.g. RawTherapee), so a small-Gaussian approximation is the standard, defensible choice rather than a compromise specific to this implementation. Pushing Amount/Radius far enough does show visible ringing at hard edges (the maxStep cap bounds it, it doesn't hide it) — that is the real algorithm's known failure mode surfacing, not a bug. |

| R5 — Naga single-source shaders (WGSL→WGPU desktop + generated GLSL ES 3.0 web/iOS) | **Spike, not the full item, was run 2026-08-31** — verdict: don't pursue. Real findings, not guessed: (1) `naga` (crate `naga` 30.0.1, part of the `gfx-rs/wgpu` monorepo, actively maintained) DOES translate real WGSL→GLSL ES 3.00 — verified hands-on: `cargo install naga-cli`, hand-ported the `comp` fragment shader's core math (s2l/l2s, screen blend, the BT.2390 knee, the post-print sat/vibrance step — same operations, same order, not reinvented) to WGSL, ran `naga --profile es300 --entry-point fs_main comp.wgsl out.frag`, got back real `#version 300 es` GLSL. Naga preserves evaluation order faithfully (every intermediate becomes an explicit `_eN` temp in source order, no visible reassociation) — good for determinism. (2) A real precision caveat, measured not assumed: naga constant-folded `1.0/2.4` to the literal `0.41666666` (8 significant digits) in the generated GLSL, one representation short of `0.416666666666667` — for a shader family whose test suite requires byte-exact PNGs (`test/export_harness.mjs`'s 18 goldens), every such folded constant would need auditing. (3) wgpu's own docs list the GLSL backend as **secondary support**, not primary (WebGPU/Vulkan/Metal/D3D12 are primary); `gfx-rs/naga`'s issue tracker has real, open glsl-out-specific bugs (e.g. #589 mismatched outputs, #2380 wrong array return type, #1457 vertex-order mismatch vs `glslc`) — none hit by this shader slice, but the backend is not battle-hardened the way naga's WGSL/SPIR-V paths are. (4) The bigger finding, checked directly (`grep -rl wgpu\|WGSL desktop/src-tauri/src/` → empty): **the desktop shell has no native GPU shader renderer to unify with.** `desktop/` is a Tauri wrapper around the system WebView (WKWebView on macOS), and it runs the exact same `chromasmith-22.html` — including the same WebGL2 GLSL — as the web build (`main.rs`'s own comments confirm this; RAW decode is native Rust specifically *because* the WebView can't do it, not because rendering is native). So R5's original premise — "two hand-maintained shader copies across web and desktop" — does not describe this codebase's actual architecture; there is only ever one GLSL copy today, reused for free via the WebView. Adding a real WGPU desktop renderer would be a **net-new second rendering pipeline**, not a maintenance reduction, and would reopen exactly the pixel-parity risk the `toString`-generated CPU worker (CLAUDE.md §2) was built to avoid for the *existing* single pipeline. (5) Cost: `naga-cli` alone pulls ~25 transitive crates and a real build step (WGSL source → codegen → paste into the JS template literal) — a genuine addition against this repo's explicit "no build step" constraint (CLAUDE.md §1/§2), for a payoff (a desktop renderer that doesn't currently exist) nobody asked for. **Decision: do not wire naga into the app.** No shader/toggle code was landed — the WGSL/GLSL spike files live outside the repo (`/tmp`) and were not committed. If a genuine second GPU backend is ever wanted (e.g. a real native desktop window instead of a WebView), naga is a credible tool for it — but that is a different, much bigger proposition than "de-duplicate two shader copies," since no second copy exists to de-duplicate. |
| N2.2 — Cleanup-pass fusion in `raw_decode.rs` | **Investigated 2026-08-31, premise was wrong.** The roadmap named `denoise_shadows_rgb16`, `suppress_false_color`, and `hue_defringe_gated` as pointwise-fusion candidates — read all three end to end, and none are pointwise: `denoise_shadows_rgb16` averages a 7×7 neighbourhood per shadow pixel, `suppress_false_color` gates on a 5×5 max-min local-contrast window then runs up to 8 iterations of a 3×3 median filter, and `hue_defringe_gated` gates on that same kind of 5×5 contrast window before its (otherwise pointwise) hue-desaturate step. Every candidate needs neighbour reads somewhere, so there is no set of currently-separate passes whose output depends only on the same input pixel — "merge the pointwise traversals" has nothing to merge. (One narrower, real optimisation was noticed but NOT attempted: `suppress_false_color` preserves luma exactly by construction, so `hue_defringe_gated`'s own contrast computation is mathematically redundant with one already computed a function earlier — reusing it would mean threading intermediate f32 buffers across a function boundary and reasoning about u16-quantisation rounding at each stage to stay byte-exact, a real but much smaller and riskier change than what N2.2 described, better scoped as its own item if ever pursued.) No code was changed, no test added — nothing to verify. |
| A full 16-bit render pipeline as the route to better highlights | Measured directly: ≤1/255 difference. Bit depth was never the gap — headroom is (see R1). Don't re-litigate this as a precision problem. |
| Chasing camera colour breadth by hand-calibrating bodies | Use rawler's embedded per-camera matrices instead — same well every other converter draws from (see R8, shipped). |
| Lifting any RapidRAW source | AGPL-3.0. Their published ideas/benchmarks are fair game; their code is not. |
| A WGSL/WGPU renderer port purely for slider-latency speed | RapidRAW's own headline "20fps→120fps" win was deleting a JPEG-over-IPC round trip this app never had (it renders in-page already). R5's own spike (see above) has since concluded there is no second shader copy to unify in the first place. |

### RapidRAW competitive review

Source: a review of [CyberTimon/RapidRAW](https://github.com/CyberTimon/RapidRAW) against this
codebase. Full working notes: `~/.claude/plans/can-you-review-rapidraw-virtual-glacier.md`.

**Findings still worth keeping:**
- Both stacks are Rust + Tauri 2 + rawler + Lensfun + ONNX — the divergence is only render
  surface and pixel precision, not architecture.
- Every native competitor (darktable, RawTherapee, Lightroom/C1/DxO) is desktop-only; our
  WebGL2 choice is what buys web *and* iOS, which none of them have — not a disadvantage to fix.
- Apps shipping both desktop and mobile do it via one kernel source, machine-translated (Dehancer's
  `dehancer-gpulib-cpp`, Lightroom's shared C++ core). Nobody hand-maintains two shader copies —
  R5 (Naga) was the sanctioned path there — its spike concluded 2026-08-31 that no second shader
  copy exists to unify (the desktop shell reuses the same WebGL2/GLSL via its WebView), so this
  route is closed; see the Rejected/withdrawn table.
- RapidRAW's film emulations run scene-referred inside their own WGSL shader, and their whole
  pipeline is 32-bit throughout — same direction R1 took, independently confirmed by darktable
  ("all core functions operate on 4×32-bit float buffers... pixels prepared for display only at
  the last stage").
- Licensing: RapidRAW is AGPL-3.0 (ideas fair game, code isn't); Spektrafilm profiles are
  CC BY-SA 4.0 (attribution + share-alike).
